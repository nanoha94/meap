# レシピ公開機能 仕様書

## 1. 機能概要

### 1.1 目的

レシピをグループ内だけでなく、アカウントを持っていないユーザー（匿名ユーザー）にも閲覧可能にする機能を追加する。

### 1.2 基本方針

-   **保存** = グループ内全員アクセス可能（即時共有）、外部には公開されない
-   **外部公開** = ログインの有無にかかわらず、誰でも閲覧可能（明示的な操作）

### 1.3 公開データの管理

-   外部公開後、レシピを編集して「保存」を押下しても、外部公開データは変更されない（グループ内のみ更新）
-   「外部公開」ボタン押下で、現在のレシピデータを外部公開データに反映
-   外部公開データは公開時の状態を固定するため、別テーブルで管理する

### 1.4 レシピ編集ページのボタン

-   **保存**: グループ内のみ更新（外部公開データは変更されない）
-   **外部公開**:
    -   未保存の場合は、保存して外部公開
    -   既に外部公開済みの場合は、外部公開データを更新

## 2. 権限管理

### 2.1 レシピ単位の編集責任者

各レシピには**編集責任者**が設定される。

-   レシピ作成時に、作成者が自動的に編集責任者となる
-   編集責任者の変更は、現在の編集責任者のみが可能
-   **編集責任者の変更条件:**
    -   **外部公開前**（`status = 'limited'`）: 変更可能
    -   **外部公開中**（`status = 'public'`）: 変更不可
    -   **外部公開解除後**（`status = 'limited'`に戻った場合）: 変更可能

### 2.2 編集責任者と公開レシピの作成者

-   **編集責任者**（`owner_user_id`）: 現在の編集責任者（変更条件あり）
-   **公開レシピの作成者**: 外部公開時の`owner_user_id`を`published_recipes`テーブルに保存（変更不可）

**編集責任者の変更ルール:**

-   **外部公開前**（`status = 'limited'`）: 編集責任者を変更可能
-   **外部公開中**（`status = 'public'`）: 編集責任者を変更不可（一度外部公開を解除すれば変更可能）
-   公開レシピの作成者表示: `published_recipes`テーブルの`owner_user_id`を使用（外部公開時の編集責任者）
-   グループ内レシピの表示: 現在の編集責任者（`owner_user_id`）を表示

### 2.3 操作権限

| 操作                               | 編集責任者 | グループ内メンバー（編集責任者以外） | グループ外ユーザー（ログイン済み） | 匿名ユーザー |
| ---------------------------------- | ---------- | ------------------------------------ | ---------------------------------- | ------------ |
| レシピ閲覧（グループ内）           | ✅         | ✅                                   | ❌                                 | ❌           |
| レシピ編集                         | ✅         | ✅                                   | ❌                                 | ❌           |
| レシピ削除                         | ✅         | ❌                                   | ❌                                 | ❌           |
| 保存（グループ内のみ更新）         | ✅         | ✅                                   | ❌                                 | ❌           |
| 外部公開                           | ✅         | ❌                                   | ❌                                 | ❌           |
| 公開データ更新                     | ✅         | ❌                                   | ❌                                 | ❌           |
| 公開取り消し                       | ✅         | ❌                                   | ❌                                 | ❌           |
| 編集責任者の変更（外部公開前のみ） | ✅         | ❌                                   | ❌                                 | ❌           |
| 外部公開済みレシピ閲覧             | ✅         | ✅                                   | ✅                                 | ✅           |

## 3. データベース設計

### 3.1 公開レシピデータの構造

公開レシピは以下のテーブルで管理される：

-   `published_recipes`: 基本情報（レシピ名、URL、メモ、分量、作成者情報など）
-   `published_categories`: カテゴリーマスタ（ユニークなカテゴリー名を管理）
-   `published_ingredients`: 食材マスタ（ユニークな食材名を管理）
-   `published_recipe_category_mappings`: レシピとカテゴリーの多対多リレーション
-   `published_recipe_ingredient_mappings`: レシピと食材の多対多リレーション
-   `published_recipe_steps`: 手順（画像 ID を含む）

**データの特徴:**

-   カテゴリーと食材はマスタテーブルで管理し、同じ名称のものは統一される（データの正規化）
-   外部公開時の編集責任者情報（`owner_user_id`）を`published_recipes`テーブルに保存（`users`テーブルから JOIN して名前を取得）
-   外部公開時の状態を固定するため、元のレシピが変更されても公開データは変更されない
-   カテゴリーと食材はマスタテーブルの ID で JOIN して検索・絞り込み可能

## 4. API 設計

### 4.1 グループ内レシピエンドポイント（認証必須）

#### 4.1.1 レシピ一覧取得

```
GET /api/recipes
```

**認証:** 必須

**パラメータ:**

-   `page` (optional): ページ番号（デフォルト: 1）
-   `per_page` (optional): 1 ページあたりの件数（デフォルト: 15）

**動作:**

-   グループ内のレシピ一覧を取得
-   編集可能な情報も含む

**レスポンス:**

```json
{
  "success": true,
  "data": [
    {
      "id": "uuid",
      "name": "レシピ名",

      "lastPublishedAt": null,
      "ownerUserId": "uuid",
      "isOwner": true,
      "thumbnail": {...},

      ...
    }
  ]
}
```

**動作:**

### 4.2 公開レシピエンドポイント（認証不要、認証ありでもアクセス可能）

#### 4.2.1 公開レシピ一覧取得

```
GET /api/public/recipes
```

**認証:** 不要（認証ありでもアクセス可能）

**パラメータ:**

-   `page` (optional): ページ番号（デフォルト: 1）
-   `per_page` (optional): 1 ページあたりの件数（デフォルト: 15）
-   `category` (optional): カテゴリー名でフィルタリング（`search_filters.filter_value`で管理された検索条件を使用）

-   `ownerUserId` (optional): 作成者のユーザー ID でフィルタ（特定ユーザーの公開レシピ一覧を取得）

**動作:**

-   公開済みレシピ一覧を取得（`status = 'public'`のレシピのみ、グループ内外問わず）

### 4.5 認証必須エンドポイント（既存拡張）

#### 4.5.1 レシピ作成（変更なし）

```
POST /api/recipes
```

**リクエストボディ（変更なし）:**

```json
{
  "name": "レシピ名",
  "url": "レシピURL",
  "memo": "メモ",
  "servingCount": 4,
  "thumbnailId": "uuid",
  "categoryIds": ["uuid"],
  "ingredients": [...],
  "steps": [...]
}
```

**動作:**

-   `status = 'limited'`で作成
-   `owner_user_id`に現在のユーザー ID を設定（作成者が編集責任者となる）

#### 4.5.2 レシピ更新（保存）

```
PUT /api/recipes/{id}
```

**権限:** グループ内メンバー（編集責任者以外も可）
**注意:** `ownerUserId`を変更する場合は、現在の編集責任者のみ可能、かつ外部公開中（`status = 'public'`）の場合は変更不可

**リクエストボディ:**

```json
{
  "name": "レシピ名",
  "url": "レシピURL",
  "memo": "メモ",
  "servingCount": 4,
  "thumbnailId": "uuid",
  "categoryIds": ["uuid"],
  "ingredients": [...],
  "steps": [...],
  "ownerUserId": "uuid" // オプション: 編集責任者を変更する場合（外部公開前のみ変更可能）
}
```

**動作:**

-   `recipes`テーブルのみ更新（グループ内のデータを更新）
-   `published_recipes`は変更されない（外部公開データは変更されない）
-   外部公開済みの場合、グループ内データと外部公開データに差異が生まれる
-   `ownerUserId`が指定された場合:
    1. レシピの`status`が`'public'`（外部公開中）の場合はエラーを返す（編集責任者の変更不可）
    2. 現在のユーザーが編集責任者であることを確認
    3. 指定されたユーザーがグループ内メンバーであることを確認
    4. `recipes.owner_user_id`を更新

#### 4.5.3 外部公開（保存して外部公開 / 外部公開データ更新）

```
POST /api/recipes/{id}/publish
```

**権限:** 編集責任者のみ

**リクエストボディ:**

```json
{
    "save": true // 未保存の場合はtrue、既に保存済みの場合は省略可
}
```

**動作:**

1. 未保存の場合（`save: true`が指定された場合）:
    - まず`recipes`テーブルを更新（保存処理）
2. レシピの現在の状態を取得
3. `published_recipes`テーブルに基本情報を保存（新規）または更新（既存）
    - `published_recipes.recipe_id`で既存レコードを検索（存在する場合は更新、存在しない場合は新規作成）
    - `recipe_id`に現在の`recipes.id`を設定
    - `owner_user_id`に現在の`recipes.owner_user_id`を設定
    - 作成・更新後、`recipes.published_recipe_id`に`published_recipes.id`を設定
4. カテゴリー・食材のマスタテーブル処理（パフォーマンス最適化版）:
    - 名称の正規化（前後の空白削除、全角半角統一など）
    - マスタテーブルを一括検索（`whereIn`でバッチ処理）
    - 存在しない名称を一括作成（`insert`でバッチ処理）
    - マッピングテーブルに一括挿入（既存データを削除して再作成）
5. 画像のコピー処理:
    - サムネイル画像: 元の画像を`images/published/{published_recipe_id}/`にコピーし、新しい`Image`レコードを作成
    - 手順画像: 各手順の画像を`images/published/{published_recipe_id}/`にコピーし、新しい`Image`レコードを作成
    - `published_recipes.thumbnail_image_id`と`published_recipe_steps.step_image_id`に新しい画像 ID を設定
6. `published_recipe_steps`テーブルに手順を保存（既存データを削除して再作成）
7. `recipes.status = 'public'`に更新（未公開の場合）
8. `published_recipes.published_at`を現在時刻に設定（新規公開の場合）
9. `published_recipes.last_published_at`を現在時刻に更新（既に公開済みの場合）

**レスポンス:**

```json
{
    "success": true,
    "message": "レシピを外部公開しました", // または "外部公開データを更新しました"
    "data": {
        "id": "uuid",
        "status": "public",
        "publishedAt": "2025-01-05T12:00:00Z",
        "lastPublishedAt": "2025-01-06T12:00:00Z"
    }
}
```

#### 4.5.4 公開取り消し

```
DELETE /api/recipes/{id}/publish
```

**権限:** 編集責任者のみ

**動作:**

1. `recipes.status = 'limited'`に更新
2. `published_recipes.recipe_id`で`published_recipes`のレコードを検索して削除
    - `published_recipe_categories`, `published_recipe_ingredients`, `published_recipe_steps`も自動削除される（CASCADE）
    - 公開画像（`images/published/{published_recipe_id}/`配下）も削除
3. `recipes.published_recipe_id`を NULL に設定

**レスポンス:**

```json
{
    "success": true,
    "message": "外部公開を取り消しました"
}
```

#### 4.5.5 レシピ削除（拡張）

```
DELETE /api/recipes/{id}
```

**権限:** 編集責任者のみ（変更）

**変更点:**

-   既存の削除処理に以下を追加:
    -   `recipes`レコード削除時、`ON DELETE CASCADE`で`published_recipes`レコードも自動削除
    -   `published_recipe_categories`, `published_recipe_ingredients`, `published_recipe_steps`も自動削除される（CASCADE）
    -   公開画像（`images/published/{published_recipe_id}/`配下）も削除
-   権限チェックを追加（編集責任者のみ削除可能）

**レスポンス（変更なし）:**

```json
{
    "success": true,
    "message": "レシピを削除しました"
}
```

## 4.6 追加が必要な API 一覧

### グループ内レシピエンドポイント（認証必須）

1. ✅ **レシピ一覧取得** - `GET /api/recipes`（レスポンス拡張）
2. ✅ **レシピ詳細取得** - `GET /api/recipes/{id}`（レスポンス拡張）

### 公開レシピエンドポイント（認証不要、認証ありでもアクセス可能）

3. ✅ **公開レシピ一覧取得** - `GET /api/public/recipes`（新規、`ownerUserId`パラメータでフィルタリング可能）
4. ✅ **公開レシピ詳細取得** - `GET /api/public/recipes/{id}`（新規）
5. ✅ **特定ユーザーの公開レシピ一覧取得** - `GET /api/public/users/{userId}/recipes`（新規）
6. ✅ **検索フィルタ候補取得** - `GET /api/public/search-filter-options`（新規）

### 認証必須エンドポイント（既存拡張）

7. ✅ **レシピ作成** - `POST /api/recipes`（`owner_user_id`の設定を追加）
8. ✅ **レシピ更新（保存）** - `PUT /api/recipes/{id}`（権限: グループ内メンバー、`ownerUserId`変更時は編集責任者のみ、外部公開中は変更不可）
9. ✅ **レシピ削除** - `DELETE /api/recipes/{id}`（権限: 編集責任者のみに変更）
10. ✅ **外部公開** - `POST /api/recipes/{id}/publish`（新規、`published_recipes`テーブルに`owner_user_id`を保存）
11. ✅ **公開取り消し** - `DELETE /api/recipes/{id}/publish`（新規）

### 実装時の注意点

-   `/api/recipes` は認証必須、グループ内レシピのみ取得（`recipes`テーブルから）
-   `/api/public/recipes` は認証不要、認証ありでもアクセス可能、公開レシピのみ取得（`published_recipes`テーブルから）
-   すべてのエンドポイントで適切な権限チェックを実装
-   レスポンスに権限情報（`isOwner`, `canEdit`, `canDelete`, `canPublish`）を含める（認証ありの場合のみ）
-   外部公開データとグループ内データの差分チェック（`hasUnpublishedChanges`）を実装
-   公開レシピの検索は、マスタテーブル（`published_categories`, `published_ingredients`）とマッピングテーブルで検索する
-   カテゴリーと食材はマスタテーブルで管理され、同じ名称のものは統一される（データの正規化）
-   絞り込み候補は`search_filter_options`テーブルで管理（初期はデータベース直接変更）

### 検索の実装方法

リレーショナルテーブルで管理するため、通常の SQL 検索が可能。

**カテゴリー検索の例（`search_filters`と`search_filter_options`を使用）:**

```sql
-- 「和食」で検索する場合、search_filtersから検索フィルタを取得し、
-- 対応するsearch_filter_optionsから検索対象のカテゴリー名を取得
-- 例: filter_value = '和食'に対して、category_nameに「和食」「日本食」「日本料理」が登録されている場合
SELECT DISTINCT pr.* FROM published_recipes pr
INNER JOIN published_recipe_category_mappings prcm ON pr.id = prcm.published_recipe_id
INNER JOIN published_categories pc ON prcm.category_id = pc.id
INNER JOIN search_filter_options sfo ON pc.name LIKE CONCAT('%', sfo.category_name, '%')
INNER JOIN search_filters sf ON sfo.search_filter_id = sf.id
WHERE pr.status = 'public'
  AND sf.filter_value = '和食'
  AND sf.type = 'category'
  AND sf.is_active = true;
```

**食材検索の例:**

-- 食材名に「鶏肉」が含まれるレシピを検索

INNER JOIN published_ingredients pi ON prim.ingredient_id = pi.id

## 6. 公開処理の実装

### 6.1 カテゴリー・食材のマスタテーブル処理

**処理フロー（パフォーマンス最適化版）:**

```php
// 1. 名称の正規化（前後の空白削除、全角半角統一など）
$normalizedCategoryNames = array_map('normalizeName', $categoryNames);
$normalizedIngredientNames = array_map('normalizeName', $ingredientNames);

// 2. バッチでマスタテーブルを一括検索（IN句を使用）
$existingCategories = PublishedCategory::whereIn('name', $normalizedCategoryNames)
    ->pluck('id', 'name')
    ->toArray();
$existingIngredients = PublishedIngredient::whereIn('name', $normalizedIngredientNames)
    ->pluck('id', 'name')
    ->toArray();

// 3. 存在しない名称を抽出
$newCategoryNames = array_diff($normalizedCategoryNames, array_keys($existingCategories));
$newIngredientNames = array_diff($normalizedIngredientNames, array_keys($existingIngredients));

// 4. 新規カテゴリー・食材を一括作成（bulk insert）
if (!empty($newCategoryNames)) {
    PublishedCategory::insert(
        array_map(fn($name) => ['name' => $name, 'created_at' => now(), 'updated_at' => now()], $newCategoryNames)
    );
    // 作成したレコードを取得して既存配列にマージ
    $newCategoryRecords = PublishedCategory::whereIn('name', $newCategoryNames)
        ->pluck('id', 'name')
        ->toArray();
    $existingCategories = array_merge($existingCategories, $newCategoryRecords);
}

if (!empty($newIngredientNames)) {
    PublishedIngredient::insert(
        array_map(fn($name) => ['name' => $name, 'created_at' => now(), 'updated_at' => now()], $newIngredientNames)
    );
    $newIngredientRecords = PublishedIngredient::whereIn('name', $newIngredientNames)
        ->pluck('id', 'name')
        ->toArray();
    $existingIngredients = array_merge($existingIngredients, $newIngredientRecords);
}

// 5. マッピングテーブルに一括挿入（bulk insert）
$categoryMappings = [];
foreach ($normalizedCategoryNames as $index => $name) {
    $categoryMappings[] = [
        'published_recipe_id' => $publishedRecipeId,
        'category_id' => $existingCategories[$name],
        'order' => $index,
    ];
}
PublishedRecipeCategoryMapping::insert($categoryMappings);

$ingredientMappings = [];
foreach ($normalizedIngredientNames as $index => $name) {
    $ingredientMappings[] = [
        'published_recipe_id' => $publishedRecipeId,
        'ingredient_id' => $existingIngredients[$name],
        'quantity' => $ingredients[$index]['quantity'] ?? null,
        'unit' => $ingredients[$index]['unit'] ?? null,
        'order' => $index,
    ];
}
PublishedRecipeIngredientMapping::insert($ingredientMappings);
```

**パフォーマンス最適化のポイント:**

1. **バッチ処理（一括取得）**: `whereIn`で一括検索し、N+1 問題を回避
2. **インデックスの設定**: `published_categories.name`と`published_ingredients.name`にユニークインデックスを設定
3. **一括挿入（Bulk Insert）**: `insert()`で一括作成・挿入
4. **名称の正規化**: 前後の空白削除、全角半角統一
5. **トランザクション処理**: 公開処理全体をトランザクションで囲む

**想定される処理時間:**

-   カテゴリー 5 個、食材 10 個の場合: 約 5-10ms（インデックスあり + バッチ処理）

**マイグレーションでのインデックス設定:**

```php
Schema::create('published_categories', function (Blueprint $table) {
    $table->uuid('id')->primary();
    $table->string('name')->unique(); // ユニークインデックス
    $table->timestamps();

    $table->index('name'); // 検索用インデックス（ユニークでも自動的に作成されるが明示的に指定）
});

Schema::create('published_ingredients', function (Blueprint $table) {
    $table->uuid('id')->primary();
    $table->string('name')->unique(); // ユニークインデックス
    $table->timestamps();

    $table->index('name'); // 検索用インデックス
});

Schema::create('search_filters', function (Blueprint $table) {
    $table->uuid('id')->primary();
    $table->enum('type', ['category', 'ingredient']);
    $table->string('filter_value'); // 検索フィルタの値（例: "和食"）
    $table->integer('display_order')->default(0); // 表示順
    $table->boolean('is_active')->default(true); // 有効/無効
    $table->timestamps();

    $table->index(['type', 'is_active', 'display_order']);
    $table->unique(['type', 'filter_value']); // 同じtypeで同じfilter_valueは1つだけ
});

Schema::create('search_filter_options', function (Blueprint $table) {
    $table->uuid('id')->primary();
    $table->uuid('search_filter_id');
    $table->string('category_name'); // 検索対象のカテゴリー名
    $table->timestamps();

    $table->foreign('search_filter_id')->references('id')->on('search_filters')->onDelete('cascade');
    $table->index('search_filter_id');
    $table->index('category_name');
});
```

### 6.2 画像の管理方法

#### 6.2.1 画像ファイルの保存場所

**保存パス:**

-   公開画像: `images/published/{published_recipe_id}/...`
-   パス例: `/storage/images/published/{published_recipe_id}/image.jpg`

**実装方法:**

-   外部公開時に、元の画像をコピーして`images/published/{published_recipe_id}/`に保存
-   公開取り消し時、公開レシピ削除時に`images/published/{published_recipe_id}/`配下の画像を削除

**理由:**

-   セキュリティが高い（グループ内画像と公開画像を完全に分離）
-   アクセス制御がシンプル（パスで公開画像かどうかを判別可能）
-   公開取り消し時の処理が明確

#### 6.2.2 データベース設計

**採用案: 既存の`images`テーブルを使用**

**理由:**

-   `published_recipes.thumbnail_image_id`と`published_recipe_steps.step_image_id`で既に`images`テーブルを参照している
-   テーブル設計がシンプル（新規テーブル不要）
-   画像のパス（`src`）で公開画像かどうかを判別可能（`/storage/images/published/...`）
-   既存の設計と整合性が高い

**テーブル構造（変更なし）:**

-   `images`テーブル: 既存のまま使用
    -   `id`: UUID（主キー）
    -   `src`: 画像 URL（パス）
    -   `width`: 画像の幅
    -   `height`: 画像の高さ
    -   `timestamps`

**画像の判別方法:**

-   グループ内画像: `src`が`/storage/images/groups/{group_id}/...`の形式
-   公開画像: `src`が`/storage/images/published/{published_recipe_id}/...`の形式

**外部キー制約:**

-   `published_recipes.thumbnail_image_id` → `images.id`（NULL 可）
-   `published_recipe_steps.step_image_id` → `images.id`（NULL 可）

**削除時の動作:**

-   `published_recipes`レコード削除時: 関連する公開画像（`images/published/{published_recipe_id}/`配下）を削除
-   `published_recipe_steps`レコード削除時: 関連する手順画像を削除（`ON DELETE SET NULL`またはアプリケーション側で削除）

**`image_mappings`テーブルについて:**

-   グループ内画像は`image_mappings`テーブルを使用（`group_id`が必須、複数画像の管理）
-   公開画像は`image_mappings`を使用しない（直接外部キーで参照、1 対 1 の関係）
-   `publish_image_mappings`のようなテーブルは不要（理由: 1 対 1 の関係で十分、グループに紐づかないため`image_mappings`の設計と合わない）

**代替案（採用しない）: `published_images`テーブルを新規作成**

-   公開画像専用のテーブルを作成する案も検討したが、既存の`images`テーブルで十分対応可能なため採用しない
-   テーブルが増えることで設計が複雑になり、`published_recipes`と`published_recipe_steps`の外部キーを変更する必要がある
